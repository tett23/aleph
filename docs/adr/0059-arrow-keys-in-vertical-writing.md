# ADR 0059: 縦書きの矢印キーを、見た目の向きに合わせる

ステータス: 採択

## 文脈

エディタは、カーソルの移動と範囲の選択をブラウザの `contenteditable` に任せている（[ADR 0019](0019-one-editor-for-both-writing-modes.md)）。
[ADR 0019](0019-one-editor-for-both-writing-modes.md) は、縦書きの矢印キーの向きについて「上下が行の中、左右が行のあいだ」になると見込み、それもブラウザに決めさせた。

実際の WebKit は、その逆に動く。
main（da2d336）のデバッグのビルドで、試験のプロジェクトの章を縦書きで開いて確かめた。
↑↓ を押すと、カーソルは行のあいだを動いた（行 43 で ↓ を押すと行 44 の頭へ、↑ を 2 回押すと行 42 へ）。
←→ を押すと、カーソルは行の中を一字ずつ動いた（行 44 の頭で ← を押すと、前の行 43 の末尾へ戻った）。
WebKit は、矢印キーを書字方向に関係なく、↑↓ を「行」、←→ を「字」として扱っている。

縦書き（`vertical-rl`）では、字は上から下へ、行は右から左へ進む。
見た目に合う動きは、↓ で次の字、↑ で前の字、← で次の行、→ で前の行である。
いまのままでは、書き手は押したのと違う向きにカーソルが動くのを見ることになる。

キーは、エディタの要素の `keydown`（[app/ed/view.ts](https://github.com/tett23/aleph/blob/da2d336/app/ed/view.ts#L456)）で受ける。
変換中のキーを IME に渡したあと、エディタのキー（[app/ed/editor.ts](https://github.com/tett23/aleph/blob/da2d336/app/ed/editor.ts#L186)）に回し、取らなかったキーはブラウザの既定の動きに任せている。
補完のウィンドウが開いているときは、↑↓ で候補を選ぶ。

ブラウザの `Selection.modify(alter, direction, granularity)` を使えば、キーを押さずに、カーソルを「字」「語」「行」などの単位で前後に動かせる。
WebKit が ↓ で次の行へ動かすのは「行の単位で前へ」の移動なので、縦書きでも `modify` の「行」は次の行へ動くと見込める。
ただし、縦書きでの `modify` の動きは、まだ WebView で確かめていない。

## 実装すること

- 縦書きのときだけ、エディタが矢印キーを受け持つ。横書きはこれまでどおりブラウザに任せる。
- 受け持つ順は次のとおりとする。
  - 変換中のキーは、これまでどおり IME に渡す（`swallowKey`）。
  - 補完のウィンドウが開いているあいだの ↑↓ は、これまでどおり候補を選ぶ。
  - そのほかの矢印キーを、下の表のとおりに `Selection.modify` で動かし、ブラウザの既定の動きを止める（`preventDefault`）。
  - 動かしたあと、DOM の選択を文書の位置に直して状態に持ち、カーソルが見えるようにスクロールする。
- キーを、横書きのときの同じ動きに回して読む。
  - ↓ は横書きの →（前へ、字の単位）、↑ は ←（後ろへ、字の単位）。
  - ← は横書きの ↓（前へ、行の単位）、→ は ↑（後ろへ、行の単位）。
- 修飾キーで単位を変える。macOS の横書きの動きに合わせる。

  | キー | 何もなし | ⌥ | ⌘ |
  | --- | --- | --- | --- |
  | ↓ | 前へ、字（`character`） | 前へ、語（`word`） | 前へ、行の端（`lineboundary`） |
  | ↑ | 後ろへ、字 | 後ろへ、語 | 後ろへ、行の端 |
  | ← | 前へ、行（`line`） | 前へ、段落の端（`paragraphboundary`） | 文書の末尾 |
  | → | 後ろへ、行 | 後ろへ、段落の端 | 文書の頭 |

  - ⇧ を足すと、動かす代わりに選択を伸ばす（`extend`）。
  - ⌃ を含む組み合わせと、⌘ と ⌥ を同時に押した組み合わせは、受け持たずにブラウザに任せる。
- ⌘← と ⌘→（文書の末尾と頭）は、`modify` を使わず、状態の選択を文書の末尾（または頭）に置き、その行までスクロールする。表示を仮想化しているので、描いていない行にはブラウザの移動が届かないからである。⇧ を足したときは、選択の起点を残して伸ばす。
- キーと修飾キーから動かし方を決める関数を、DOM に触れない純粋な関数として分ける（たとえば `app/ed/vmove.ts`）。
  - 受け取るもの：`key` と、⇧、⌥、⌘、⌃ のそれぞれを押しているか。
  - 返すもの：`{ alter: "move" | "extend", direction: "forward" | "backward", granularity }` か、文書の端への移動か、受け持たないことを表す `null`。
- 仕様書のエディタの節に、縦書きの矢印キーの向きを書き、ADR の表にこの ADR の行をリンク付きで足す。
- [ADR 0019](0019-one-editor-for-both-writing-modes.md) のステータスの行に、カーソルの移動のうち縦書きの矢印キーの向きをこの ADR で置き換えたと書く。

## 実装しないこと

- 横書きの矢印キーの動きを変えること。
- 矢印キーの向きを、設定で選べるようにすること。
- ⌃N、⌃P、⌃F、⌃B などの Emacs 風のキーを、縦書きに合わせて回すこと。これらは「次の行」「次の字」という意味で押すキーなので、ブラウザの動きのままでも意味に合う。
- Page Up と Page Down、Home と End を変えること。

## テスト設計

`node --test` で、テストを先に書いて失敗させてから実装する。

- 動かし方を決める関数が、次を返すこと。
  - 修飾キーなしの ↓、↑、←、→ が、それぞれ「前へ、字」「後ろへ、字」「前へ、行」「後ろへ、行」の `move` になること。
  - ⌥ を足すと、↓↑ が語の単位、←→ が段落の端になること。
  - ⌘ を足すと、↓↑ が行の端、← が文書の末尾、→ が文書の頭になること。
  - ⇧ を足すと、同じ向きと単位のまま `extend` になること。⇧⌘← と ⇧⌘→ が、選択を伸ばす文書の端への移動になること。
  - ⌃ を含む組み合わせ、⌘⌥ の組み合わせ、矢印でないキーで `null` になること。
- 画面の確かめ方：試験のプロジェクトの章を縦書きで開き、次を確かめる。
  - ↓↑ で行の中を一字ずつ動き、行の末尾で ↓ を押すと次の行の頭へ移ること。
  - ←→ で行のあいだを動き、空の行と、改ページの見積もりの印をまたげること。押しても画面だけがスクロールすることはないこと。
  - ⇧ を足すと選択が伸びること。
  - ⌘↓↑ で行の端へ、⌘←→ で、描いていない行のある長い章でも文書の末尾と頭へ移ること。
  - 補完のウィンドウが開いているあいだは、↑↓ で候補を選べること。
  - SKK で変換しているあいだの矢印キーは、これまでどおり変換に使われること。
  - 横書きの矢印キーの動きが変わらないこと。
  - ステータスバーの「行 n, 列 m」がカーソルに付いてくること。

## トレードオフ

- 縦書きのカーソルの移動の一部を、ブラウザから取り上げて自分で持つ。ブラウザの動きが将来変わっても追従しない代わりに、向きは WebKit の扱いに左右されなくなる。
- 動かすのは `Selection.modify` で、字、語、行の区切りの判断はブラウザに残す。自分で「次の行の同じ位置」を座標から求めるより、折り返し、ルビ、縦中横の扱いをブラウザに任せられる。
- `Selection.modify` は標準になっていない API である（参考文献）。WebKit と Chromium は実装している。
- 縦書きでの `Selection.modify` の動き（特に `line` と `lineboundary` の向き）は、まだ WebView で確かめていない。実装の最初に確かめ、見込みと違えば、この ADR を直す新たな ADR を書く。
- ⌘ と ⌥ の割り当ては macOS の横書きの動きを回したものなので、⌘← が「文書の末尾」になる。横書きの ⌘← は「行の頭」なので、横書きに慣れた手は戸惑う可能性がある。縦書きの見た目に合わせるほうを選ぶ。
