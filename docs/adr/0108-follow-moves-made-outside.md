# ADR 0108: Aleph の外で移したシートとフォルダに追従し、参照を更新する

Status: proposed

## 文脈

Aleph のツリーで名前を変えるか移すと、Aleph は Golem LSP に参照の編集を尋ね、編集を当ててから移す（[ADR 0070](0070-rename-sheets-and-folders-from-tree.md)、[ADR 0100](0100-move-tree-files-and-folders.md)）。
原稿の import、画像のパス、manifest の章のパス、Wiki リンクが、移した後も正しい場所を指す。

シートやフォルダは、Aleph の外でも移される。
ターミナルの `git mv` や `mv`、Finder での移動である。
今の Aleph は、これを移動として扱わない。

- 開いているシートの移動元が見張りの事象に入ると、元の場所から消えたと判定され、「ディスクにありません（ほかのアプリで消されたか、名前が変えられました）」と通知して保存を止める（[ADR 0063](0063-watch-files-changed-outside.md)）。
  フォルダごと移したときは、子のパスが事象に入らないので、この通知は保存のときまで出ない。
- 移した先のファイルは、ツリーに新しい項目として出るだけで、タブ、ノート、目標は移らない。
- 移したファイルを指す参照は、古い場所を指したまま残る。
  `golem build` は、参照先が無いというエラーで止まる。

この ADR は、Aleph が動いている間に外で移したシートとフォルダを移動として見つけ、タブなどを追従させ、書き手が選べば参照を更新すると決める。
参照の編集は、Golem LSP の `golem/planMovedReferences` で受け取る（[tett23/golem ADR 0426: 移動し終えたファイルとフォルダの参照の編集を Golem LSP が返す](https://github.com/tett23/golem/blob/main/docs/adr/0426-plan-reference-edits-after-a-move.md)）。

## 調査した事項

origin/main（[78954b2](https://github.com/tett23/aleph/commit/78954b2825f5056d0a0a023942265ae807c63512)）で、次のことを確かめた。

- FSEvents のストリームは `FILE_EVENTS | NO_DEFER | WATCH_ROOT` で作っている（[src-tauri/src/fsevents.rs#L198](https://github.com/tett23/aleph/blob/78954b2825f5056d0a0a023942265ae807c63512/src-tauri/src/fsevents.rs#L198)）。
  コールバックは、事象の ID を捨てている（[fsevents.rs#L95-L97](https://github.com/tett23/aleph/blob/78954b2825f5056d0a0a023942265ae807c63512/src-tauri/src/fsevents.rs#L95-L97)）。
- 事象は 0.1 秒の遅れで届き、Rust 側でさらに 0.2 秒まとめてから JS に送る。
  まとめた `Batch` は、パス、Git の変更の有無、走査し直すフォルダだけを持つ（[src-tauri/src/watchfs.rs#L40-L61](https://github.com/tett23/aleph/blob/78954b2825f5056d0a0a023942265ae807c63512/src-tauri/src/watchfs.rs#L40-L61)）。
  改名の旗も、ファイルの ID も、JS には届かない。
- JS は、`paths` にある開いているシートごとに `followChange` を待たずに走らせ、消えていれば保存を止めて通知を出す（[app/watchmount.ts#L91-L122](https://github.com/tett23/aleph/blob/78954b2825f5056d0a0a023942265ae807c63512/app/watchmount.ts#L91-L122)）。
- ツリーの移動は、適用の間だけ `moveLocked` で見張りの通知を無視し、適用が終わると外す（[app/tree-move-flow.ts#L181-L182](https://github.com/tett23/aleph/blob/78954b2825f5056d0a0a023942265ae807c63512/app/tree-move-flow.ts#L181-L182)）。
  ツリーの改名は `moveLocked` を立てない。
  章の書き出しは、ワークスペースの中で一時ファイルを本来の名前に変える。
- 付け替えの後の処理（最近開いたシート、プロット、メタデータ、Wiki リンク）は、`ctx.onRename` の受け手が行う。
  Wiki リンクの受け手は、`renameReferencesHandled` が偽なら自分でリンクを書き換える。
  ノートと目標の移し替えは、純関数の `planMoveMetadata` で計画し、移動先に同じ対象があれば全体を中止する。
- macOS の SDK の `FSEvents.h` で、次の値を確かめた。
  - `kFSEventStreamEventFlagItemRenamed` は `0x00000800` である。
  - `kFSEventStreamCreateFlagUseExtendedData` は `0x00000040` で、macOS 10.13 から使え、`kFSEventStreamCreateFlagUseCFTypes`（`0x00000001`）を要する。
    この旗を付けると、各事象はパス（`path`）とファイルの ID（`fileID`、inode）を持つ辞書になる。
  - `kFSEventStreamCreateFlagMarkSelf` を付けると、自分のプロセスの操作の事象に `kFSEventStreamEventFlagOwnEvent` が付く。
- 2026-11-23 に、小さなプログラムで、FileEvents、UseCFTypes、UseExtendedData、MarkSelf、遅れ 0.1 秒のストリームを APFS のディレクトリに張り、次の操作の事象を観た。
  - `mv img/a.png sub/a.png`、`git mv ch.gm sub/ch.gm`、`mv sub moved`（フォルダ）、`mv moved/ch.gm moved/CH.gm`（大文字と小文字だけ）、`mv がぎ.gm moved/ぐげ.gm`（濁点を含む名前）: どれも、ItemRenamed の事象が二つ、同じ fileID で、同じコールバックの呼び出しに、移動元、移動先の順（事象の ID が一つか二つ違い）で届いた。
    フォルダの移動では、子の事象は届かなかった。
  - 一時ファイルを本来の名前に変える保存（`.keep.tmp` を `keep.gm` に）: `.keep.tmp` と `keep.gm` の同じ fileID の対に加えて、置き換えられた元の `keep.gm` の、別の fileID の ItemRenamed が同じコールバックの呼び出しに届いた。
  - 退避の名前変え（`keep.gm` を `keep.gm~` に変え、新しい `keep.gm` を書いて `keep.gm~` を消す）: `keep.gm` と `keep.gm~` の同じ fileID の ItemRenamed と、新しい `keep.gm` の作成が、同じコールバックの呼び出しに届いた。
    このとき、移動元の `keep.gm` には新しいファイルがある。
  - Finder の移動、HFS+ や外部のボリュームでの振る舞い、NFD の名前、Aleph の書き込みと外の移動が同じパスで重なったときの OwnEvent の旗は確かめていない。
  - プログラム、動かした手順、出力は [docs/research/2026-11-23-fsevents-renames](../research/2026-11-23-fsevents-renames/) に置いた。
- 手元の開発ビルドの設定は、golem に `~/.local/bin/golem`（`golem 0.1.0-rc4`）を指している。
  rc4 は `golem/planFileMove` にも `workspace/willRenameFiles` にも応じない。

指示者は 2026-11-23 に、エディタの外での移動にも参照が追従するように求め、この ADR を書くことを認めた。

## 実装すること

### 移動を見つける

FSEvents のストリームに `UseCFTypes`、`UseExtendedData`、`MarkSelf` を足し、各事象のパス、旗、ファイルの ID、事象の ID を Rust 側で受け取る。
Rust は、一つの `Batch` の事象のうち、次のすべてを満たす二つの事象を、移動の対とする。

- 二つとも ItemRenamed の旗を持ち、OwnEvent の旗を持たない。
- 二つのファイルの ID が等しく、同じ ID の ItemRenamed がこの二つのほかに無い。
- 事象の ID の小さいほうを移動元、大きいほうを移動先とする。
- 移動元のパスは、親のディレクトリが無いか、親のディレクトリの一覧に、大文字と小文字を区別した名前で無い。
- 移動先のパスは、親のディレクトリの一覧に、大文字と小文字を区別した名前であり、その今の inode が事象のファイルの ID と等しい。
- 移動先のパスについて、同じ `Batch` に、別のファイルの ID の ItemRenamed が無い。
  これは、移動先に前からあったファイルを置き換えた場合（一時ファイルを本来の名前に変える保存や、上書きの移動）を除くためである。
- 移動元と移動先が、同じ登録済みのワークスペースの中にある。
- どちらのパスも、見張りから外している `build/` と `.git/` の下にない。

`Batch` に、移動の対の配列 `moves` を足して JS に渡す。
JS は、移動の対のうち、どちらかのパスが `moveLocked` に当たるものを捨てる。
対にならなかった事象は、今までどおり [ADR 0063](0063-watch-files-changed-outside.md) の規則で扱う。

### タブなどを追従させる

JS は、`Batch` を受けたら、移動の対を先に処理し、終えてから残りのパスを `followChange` に回す。
移動の対の移動元と移動先のパスは、`followChange` に回さない。

移動の対ごとに、移動元のパス（フォルダなら、その下のパス）で開いているシートを、移動先のパスに付け替える。
付け替えるのは、移動先の内容が、そのシートの `saved` と一致するシートだけとする。
一致すれば、そのパスの停止と通知を消し、未保存の編集を保つ。
一致しないシートは、タブだけを付け替えず、移動元のパスを `followChange` に回して [ADR 0063](0063-watch-files-changed-outside.md) の規則で扱う。
フォルダの中に一致するシートと一致しないシートが混じるときも、シートごとにこの規則で扱う。
タブ以外の付け替え、参照の計画、索引の扱いは、シートの一致に関わらず、対ごとに行う。

付け替えた後は、[ADR 0100](0100-move-tree-files-and-folders.md) のツリーの移動と同じく、`ctx.onRename` の受け手で、最近開いたシート、プレビュー、プロットの所属を付け替える。
このとき `renameReferencesHandled` を真にして、Wiki リンクの受け手が自分でリンクを書き換えないようにする。
`moveMetadataHandled` も真にして、メタデータの受け手がノートと目標のキーを自分で付け替えないようにする。
参照の書き換えは、次の節の Golem LSP の計画だけで行う。
Golem LSP のプロジェクトごとの接続も、付け替えた直後に、ツリーの移動と同じく扱う。
旧 URI を閉じて新 URI を同期し直し、その接続に同じ対の `workspace/didRenameFiles` を一度送る。
プロジェクトの境界を越えた対では、通知の代わりに接続を作り直す。
これは、次の節の参照の更新に答える前に行い、答えを待つ間もプロジェクトの索引を新しいパスに合わせておく。

ノートと目標は、`planMoveMetadata` で移し替えを計画する。
入力のプロジェクトの一覧は、今の一覧を移動の逆の写像で移動前の一覧に戻したものとする。
移動先に同じ対象のノートや目標があれば、[ADR 0100](0100-move-tree-files-and-folders.md) と同じく、ノートと目標を一件も移さず、そのことを通知する。
書き込みは、移動を伴わないメタデータの書き込みとして行い、[ADR 0100](0100-move-tree-files-and-folders.md) と同じく、書き込みの間はメモリのメタデータを凍らせ、書いた後に読み直させる。

### 参照を更新する

`Batch` の移動の対を、ワークスペースごとに分ける。
ワークスペースごとに、その中のすべての対をまとめて、Golem LSP に `golem/planMovedReferences` を一度送る。
種類で対を絞らない。
送らなかった対の移動は Golem の側で移動前に戻されず、それを指す参照が参照先の無い参照に見えて、計画の全体がエラーになるためである。
参照する原稿が無ければ、空の `groups` が返るだけである。
送る接続は、ツリーの移動と同じく、`initializationOptions.golem.fileMove` でワークスペースを登録した接続を、この計画のために作って使い、終えたら止める。
要求の欄は 0426 の型のとおりとし、プロジェクトと可視シートの一覧と開いている文書は、移動し終えた後のものを渡す。
対どうしが連鎖か入れ子になっているときは、要求を送らず、「<件数> 件の移動は、参照を更新できない組み合わせです」と通知する。

返った `groups` が空でなければ、要求ごとに一つの通知を出す。

- 文言: 対が一つなら「<移動元> を <移動先> に移したことを検出しました。<ファイルの数> 件のファイルの参照を新しい場所に更新しますか。」、二つ以上なら「<対の数> 件の移動を検出しました。<ファイルの数> 件のファイルの参照を新しい場所に更新しますか。」とする。
  ファイルの数は、`groups` の編集先のファイルの数とする。
- 選択肢: 「更新する」と「更新しない」。
- 通知は、選ぶまで消えない（sticky）。
  答えを待つ通知が残っている間に次の `Batch` が来たときは、それぞれ別の通知とし、答えた順に処理する。

「更新する」を選んだときに、編集を当てる。
当てる前に、応答の `snapshot` と、今の本文、版、一覧を照合する。
違えば計画を取り直し、[ADR 0100](0100-move-tree-files-and-folders.md) と同じく 3 回まで取り直す。
3 回で合わなければ、「参照の更新の対象が変わり続けたため、更新できませんでした」と通知し、編集を当てない。
開いているシートはエディタに、閉じているシートはディスクに当て、失敗したら [ADR 0100](0100-move-tree-files-and-folders.md) の規則で逆順に戻す。

### Golem LSP が応じないとき

Golem LSP が `golem/planMovedReferences` の契約の版 1 に応じないときは、「Golem LSP が移動後の参照の更新に対応していません」と、ワークスペースと Golem の実行ファイルの組ごとに、Aleph を起動している間に一度だけ通知し、参照は変えない。
計画がエラーで返ったときは、エラーの URI と理由を通知し、参照は変えない。
どちらの場合も、プロジェクトの接続の索引は、付け替えのときにすでに合わせてある。

### 文書

仕様書の「外部で変わったファイル」の箇条の後に、外での移動の箇条を足す。
README には、ファイルの見張りを書いた箇所が無いので、変えない。
同梱の Golem が契約に応じない間は、対応する Golem を設定で選ぶことを、仕様書とロードマップに書く。

## 実装しないこと

Aleph が動いていない間に移したものには追従しない。
次に開いたときに、移動の前後を対応づける情報が無いためである。
移動先に前からあったファイルを置き換えた移動は、移動として扱わない。
ワークスペースの外への移動と、外からの移動は、移動として扱わない。
参照の編集を、確かめずに自動で当てることはしない。
Golem LSP 以外の方法で参照を書き換えない。

## 不変条件

I1: Rust は、一つの `Batch` で、「移動を見つける」の節の Rust の条件をすべて満たす二つの事象があるとき、そしてそのときだけ、その二つを移動の対とする。
I2: JS は、どちらかのパスが `moveLocked` に当たる移動の対を捨てる。
I3: 移動の対にならない事象の扱いは、この ADR の前と一致する。
I4: 移動元で開いていたシートは、移動先の内容が `saved` と一致するときだけ移動先に付け替わり、そのとき未保存の編集は保たれ、保存は止まらず、「ディスクにありません」の通知は出ない。
I5: 「更新する」を選ぶ前に、参照の編集はエディタにもディスクにも当たらない。
I6: 編集を当てる途中で失敗したとき、当てた編集は逆順に戻るか、戻せなかったパスと理由が通知される。
I7: 移動の対を付け替えた後、参照の更新に答える前に、その対を含むプロジェクトの接続には、同じ対の `workspace/didRenameFiles` が一度だけ届くか、接続が作り直される。
I8: 移動の付け替えの間に、Wiki リンクの受け手は自分でリンクを書き換えない。
I9: 移動の付け替えの間に、メタデータの受け手は自分でノートと目標のキーを付け替えず、ノートと目標の書き込みは `planMoveMetadata` の計画からだけ行う。
I10: 一つの `Batch` の独立した移動の対は、ワークスペースごとに一つの `golem/planMovedReferences` の要求と一つの通知にまとまり、連鎖か入れ子の対を含むワークスペースには要求を送らない。

| 入力 | 期待 | 不変条件 |
| --- | --- | --- |
| 事象が空の `Batch` | 何もしない | I3 |
| ItemRenamed が一つだけ | 移動として扱わない | I1, I3 |
| 同じ ID の ItemRenamed が二つで、両方のパスに項目がある | 移動として扱わない | I1 |
| 同じ ID の ItemRenamed が二つで、移動元が無く、移動先の inode が同じ | 移動の対 | I1 |
| 同じ ID の ItemRenamed が三つ | 移動として扱わない | I1 |
| ID が違う ItemRenamed が二つ | 移動として扱わない | I1, I3 |
| フォルダの移動（子の事象なし） | フォルダの移動の対 | I1 |
| 大文字と小文字だけの改名 | 移動の対 | I1 |
| 最後のファイルを移した後に、移動元の空のフォルダを消した | 移動の対 | I1 |
| 入れ替え（`mv b c` の後に `mv a b`） | どちらも移動として扱わない | I1, I3 |
| 一時ファイルを本来の名前に変える保存 | 移動として扱わない | I1, I3 |
| 退避の名前変えと、新しいファイルの書き込み | 移動として扱わない | I1, I3 |
| 上書きの `mv` | 移動として扱わない | I1 |
| OwnEvent の付いた事象（Aleph 自身の改名、移動、書き出し） | 移動として扱わない | I1 |
| 移動先がワークスペースの外 | 移動として扱わない | I1 |
| 移動元が `build/` の下 | 移動として扱わない | I1 |
| `moveLocked` に当たる対 | 捨てる | I2 |
| 開いているシートを移し、内容が `saved` と同じ | タブが移動先に付け替わり、通知が出ない | I4 |
| 開いているシートを移し、外で内容も変えた | そのタブは 0063 の規則で扱い、ほかの付け替えと計画は行う | I3, I4 |
| 参照される画像二つを、一度に別のフォルダへ移した | 要求一つ、通知一つ | I10 |
| 連鎖の対を含む `Batch` | 要求を送らず、更新できないと通知する | I10 |
| ノートを持つシートを移した | メタデータの受け手は書き換えず、計画から書く | I9 |
| 参照される画像を移し、「更新しない」を選んだ | 参照は変わらず、`didRenameFiles` は答えの前に一度届いている | I5, I7 |
| 参照される画像を移し、「更新する」を選んだ | 参照が更新され、`didRenameFiles` は答えの前に一度届いている | I7 |
| 章を別のプロジェクトへ移した | 接続を作り直す | I7 |
| 編集の途中でディスクへの書き込みが失敗 | 当てた編集を逆順に戻す | I6 |
| Golem が契約に応じない | 通知だけで参照は変えず、`didRenameFiles` が一度届く | I5, I7 |
| Wiki リンクで指される Markdown を移した | Wiki リンクの受け手は書き換えず、Golem の計画で更新する | I8 |

## 受けいれ条件

A1: 開発ビルドで、ターミナルの `git mv` でプロジェクトの画像と章の原稿を別のフォルダへ移すと、開いているタブが移動先に付け替わり、参照の更新の通知が出る。
A2: A1 の通知で「更新する」を選ぶと、`golem build` が参照の誤りなしに通る（[tett23/golem ADR 0426: 移動し終えたファイルとフォルダの参照の編集を Golem LSP が返す](https://github.com/tett23/golem/blob/main/docs/adr/0426-plan-reference-edits-after-a-move.md) A1 を兼ねる）。
A3: Finder でフォルダを別のフォルダへ移したときも、A1 と A2 と同じになる。

## テスト設計

Rust では、`adr0108_i1_` を名前の先頭に置いたテストを `watchfs` のテストに足す。
事象の列（パス、旗、ファイルの ID、事象の ID）と、ディレクトリの一覧と inode を手で組み立て、境界の表の I1 の各行を確かめる。
加えて、事象 4 個までのすべての並びと、旗とファイルの ID とパスの有無の組み合わせを数え上げ、対の判定が I1 の条件と一致することを確かめる。

JS では、ADR 0108 I2 から I10 を名前の先頭に置いたテストを足す。
Golem LSP は今の移動のテストと同じくモックにし、タブの付け替え、通知の選択、編集の適用と戻し、`didRenameFiles` の回数、Wiki リンクの受け手の振る舞いを確かめる。
I3 は、移動の対の無い `Batch` で、この ADR の前のテストがすべて通ることで確かめる。

A1 から A3 は、対応する Golem を設定で選んだ開発ビルドで、手で確かめる。
A3 の前に、Finder の移動で事象がどう届くかを、[docs/research/2026-11-23-fsevents-renames](../research/2026-11-23-fsevents-renames/) のプログラムで観て、同じ所に記録する。
確かめた結果は、監査の記録に残す。

## トレードオフ

ファイルの ID で対を作るので、同じファイルシステムの中での移動だけを見つけられる。
コピーしてから消す移動（別のボリュームへの移動）は、移動として扱わない。

対は一つの `Batch` の中でだけ作る。
観た限りでは、改名の二つの事象は同じコールバックの呼び出しに続けて届いたが、0.1 秒と 0.2 秒のまとめの境目で二つが別の `Batch` に分かれると、対を作れない。
その場合は今までどおり、消えたシートと新しいファイルとして扱う。

移動先に前からあったファイルを置き換えた移動は扱わないので、上書きの `mv` では参照は古いまま残る。
その代わりに、ほかのエディタの保存のたびに、移動と取り違えて参照の更新を尋ねることはない。

移動先の名前が同じ `Batch` の中で空いたばかりの移動（入れ替えや順送りの改名）は、移動として扱わない。
置き換えた移動と見分けられないためで、このときも参照は古いまま残る。

同梱の Golem 0.1.0-rc4 は計画に応じないので、対応する Golem を設定で選ぶまで、外で移すと「対応していません」の通知が、ワークスペースと Golem の実行ファイルの組ごとに、Aleph を起動している間に一度出る。

参照の更新を書き手に尋ねるので、外で移すたびに通知が出る。
その代わりに、Aleph が気付かないうちに、ほかのシートの本文が書き換わることはない。
