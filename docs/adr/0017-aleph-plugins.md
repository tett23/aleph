# ADR 0017: Aleph のプラグイン

ステータス: 採択

## 文脈

メンテナーは、プラグインをサポートするようにと求めた（2026-11-07）。
Golem のプラグイン（`.wasm`）は組版に効くもので、共有ライブラリで扱う（[ADR 0014](0014-shared-library-and-assets.md)）。
この ADR で扱うのは、Aleph の画面に機能を足すプラグインである。

プロトタイプでは、アプリの設定のディレクトリの `plugins/` に置いた `.js` を ES モジュールとして読み込み、`activate(aleph)` を呼んだ。
`aleph` には、コマンドの登録、ステータスバーの項目の登録、保存のときの処理の登録、通知を持たせた。
見本として、最長の文の字数をステータスバーに出すプラグインを書いた。
読み込みに失敗したプラグインは、例外を受けて通知し、ほかのプラグインを読み続けた。
ただし、見本のプラグインを実際に読み込ませる確認はしていない。

## 実装すること

- Aleph のプラグインは、アプリの設定のディレクトリの `plugins/` に置いた `.js`（ES モジュール）とする。モジュールは `activate(aleph)` を書き出す。
- `aleph` に持たせる API は次のものに限る。
  - `registerCommand(名前, 処理)`：ツールバーのメニューに項目を足す。
  - `registerStatus(処理)`：ステータスバーに文字を足す。
  - `onSave(処理)`：保存したあとに呼ぶ。
  - `toast(文言)`：通知を出す。
  - 処理には、開いているシートのパス、形式、本文、プロジェクトを渡す。本文を書き換える API は持たない。
- プラグインの読み込みに失敗したら、そのプラグインだけを無効にして、通知と設定の画面に理由を出す。ほかのプラグインとアプリは動かし続ける。
- 設定の画面で、プラグインのフォルダの場所と、読み込んだプラグインの一覧を出し、プラグインごとに有効と無効を切り替える。
- API の版を `aleph.version` で持ち、互換を壊す変更をするときは版を上げる。

## 実装しないこと

- プラグインの配布とインストールの仕組み（レジストリ、更新）。ファイルを置くだけとする。
- プラグインの権限の分離（ファイルの読み書き、ネットワーク）。プラグインは画面と同じ権限で動く。自分で書いたか、読んで信頼したプラグインだけを置く前提とし、設定の画面にその旨を出す。
- 本文を書き換える API、エディタの拡張（色付け、溝）を足す API。使う場面が出てから別の ADR で決める。

## テスト設計

- API：偽のプラグイン（コマンド、ステータス、保存の処理を登録するもの）を読み込み、登録されたものが呼ばれることを `node --test` で確かめる。
- 失敗：例外を投げるプラグイン、`activate` のないモジュール、構文の誤りのあるファイルで、そのプラグインだけが無効になり、ほかが動くことを確かめる。
- テストの偽のプラグインと見本のプラグインは、本実装のテストの置き場所に置く（`prototype/` は消すので、そこに頼らない）。
- 画面の確かめ方：見本のプラグインをプラグインのフォルダに置いて起動し、ステータスバーに字数が出て、メニューにコマンドが出ること。

## トレードオフ

- `.js` をそのまま読み込むと、書くのは簡単だが、プラグインはアプリと同じ権限を持つ。権限の分離は、信頼できないプラグインを配る場面が出てから考える。
- API を小さくすると互換を保ちやすいが、プラグインでできることは限られる。
